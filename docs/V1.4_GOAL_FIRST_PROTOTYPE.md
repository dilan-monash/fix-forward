# v1.4 Goal-First UX prototype — product decision record

**Status:** experiment for mentor/usability review, not final scope approval

## User problem

The previous journey was technically logical but still asked users to understand the system's process. A household user usually arrives with a much simpler thought:

- “I want to repair it.”
- “Is repair worth the cost?”
- “I want to recycle it.”
- “I don't know what to do.”

v1.4 starts with those goals.

## Product principle

> **Let the user choose the goal. Keep safety as an invisible guardrail, not a bureaucratic journey.**

The quick safety/recall gate cannot be skipped. It can override the selected goal when a serious warning or possible recall exists.

## Language rules

1. Explain “product recall” before assuming the user knows the term.
2. Put the action before the data explanation.
3. Avoid “dataset”, “identifier”, “provenance”, “confidence level” and “coverage window” in the main journey.
4. Use “We didn't find your exact model in our current list” rather than “no recall.”
5. Use “Call before visiting” rather than making “unverified” the headline.
6. Keep technical evidence one click away for transparency and assessment evidence.

## Repair/recycling service experience

Primary card priority:

1. name and service type;
2. distance when current location is permitted;
3. address;
4. phone/opening hours when source contains them;
5. **Call**, **Directions**, **Website**;
6. call/check-before-travel guidance;
7. provenance/verification inside **About this listing**.

No phone/hours/photo is invented when missing.

## Geolocation decision

### Prototype behavior

- Uses the browser Geolocation API only after an explicit click.
- Stores coordinates in JS state only.
- Sends no device coordinate to Flask or Neon.
- When the map is displayed, OpenStreetMap receives ordinary tile requests for the viewed map area; this is not described as “location never leaves the device.”
- Calculates Haversine straight-line distance locally.
- Offers manual suburb/postcode fallback.

### Governance issue

Earlier I1 documentation explicitly said manual suburb selection/no device geolocation. Teaching feedback later suggested automatic suburb/current location, and usability/product discussion supports a nearby map. This prototype intentionally exposes the idea for review; it does **not** silently rewrite the approved scope.

Decision required before final release: **accept v1.4 geolocation, defer to I2, or retain manual-only I1.**

## Smart cost finder decision

The desirable UX is:

```text
brand/model text
    ↓
product resolver (exact → fuzzy/AI suggestion → brand/category fallback)
    ↓
governed price evidence
    ↓
range + evidence level + source date
```

Not:

```text
brand/model text → AI guesses a price
```

The current UI therefore demonstrates the resolver/evidence concept and keeps the existing manual comparison as a fallback, but refuses to fabricate automatic prices.

## Success criteria for usability test

A participant should be able to answer these without explanation from the tester:

- What does FixForward help me do?
- Can I start directly with repair/compare/recycle?
- What does “product recall” mean?
- Why am I answering safety questions?
- If a serious warning appears, do I know what to do?
- Can I find a service, call it and get directions without inspecting a dataset?
- Do I understand that location permission is optional?
- Can I tell whether a cost number is real evidence or unavailable?
