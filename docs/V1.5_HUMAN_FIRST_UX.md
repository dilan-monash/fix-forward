# FixForward v1.5 — Human-first usability prototype

**Status:** non-final prototype candidate
**Date:** 7 September 2026
**Purpose:** reduce user effort without weakening recall/safety guardrails.

## Product principle

A household user comes to FixForward because they want to **repair**, **compare costs**, **recycle**, or **get help deciding**. The application should not make them study the project's data architecture before doing that.

The v1.5 design therefore uses this order:

```text
Choose goal
  ↓
Identify appliance
  ↓
Short goal + product-specific safety gate
  ↓
Recall/safety override only when needed
  ↓
Go directly to Repair / Compare / Recycle
```

The guided **I'm not sure** path can ask more questions because the user explicitly asked FixForward to help decide.

## What changed from v1.4

### 1. Actions are visible in the hero
Repair, Compare, Recycle and Help me decide are now clickable before a user scrolls. The larger cards remain lower on the landing page for explanation.

### 2. Landing is no longer blocked by a cold API/database
Static UI and appliance definitions render immediately. Recall, repair-history and service data load in the background. If a user starts quickly and an earlier recall result was "unavailable", it is re-evaluated when the real recall data arrives.

### 3. Safety is shorter and goal-specific
Maximum questions:

| Goal | Maximum questions |
|---|---:|
| Repair | 4 |
| Compare | 3 |
| Recycle | 2 |
| I'm not sure | 5 |

Questions are also filtered by appliance. For example, a shaver can receive a damaged-battery question; a kettle cannot.

### 4. A Yes or Not sure answer can end the check early
Once a response is enough to change the safer next step, the interface explicitly says:

> You can stop here.

The user is not forced to answer irrelevant remaining questions. A separate **I'm not able to check this safely** option routes to cautious guidance without requiring inspection.

### 5. Every safety question has an info panel
Each question has **What does this mean?**. The panel includes:

- a simple pictogram;
- a plain-language explanation;
- an example of what the warning can look/smell/sound like;
- a reminder not to switch on, open or touch the appliance just to answer;
- quick buttons to change the answer after reading the explanation;
- **I'm still not sure — show a safer next step**.

### 6. Repair evidence is now a chart, and appears after the practical action
Repair history no longer leads the repair journey. The map and service results come first. Repair history then shows a horizontal three-part outcome visual:

- Fixed at event;
- Repairable with more work;
- Other recorded outcomes.

Actual counts and percentages are shown together. Source/sample limitations stay inside **How was this worked out?**.

### 7. Repair/recycling cards prioritise useful details
The main listing shows name, type, distance when known, address, phone/opening information when available, and actions such as Call, Directions and Show on map. Source/verification metadata stays collapsed under **About this listing**.

### 8. Uncertain recycling is not a dead end
If the user is unsure about a warning and their original goal is recycling, FixForward may show **recycling places to contact**, with a strong contact-before-moving warning. Serious/high-risk conditions still do not route to ordinary service listings.

### 9. Cost page is less like a project roadmap
The usable manual comparison is now the main feature. Automatic model/brand pricing is described briefly as future work. FixForward explicitly refuses to invent an automatic dollar estimate without trustworthy evidence.

### 10. Accessibility noise reduced
The entire app container is no longer an `aria-live` region. Specific changing areas (toast/service results/comparison result) retain appropriate live/status semantics, avoiding unnecessarily reading an entire page after each navigation. Safety help headings are programmatically focusable when opened.

### 11. The map waits until it is useful
Opening Repair/Recycle no longer loads the third-party map library immediately. FixForward first asks for a location/suburb and only loads the map when there are results worth plotting. This reduces unnecessary network/privacy exposure and removes an empty map from the first task screen.

### 12. Back/edit state is safer
Changing appliance family/category clears stale safety/decision/cost state. Browser Back after an unable-to-check result keeps the reason for that cautious result until the user actually changes an answer.

### 13. Conservative water-ingress rule restored
Water/moisture ingress is treated as a serious stop-use warning under the I1 safety baseline. Heat and repeated power-trip/noise warnings remain differentiated caution cases, so not every Yes is treated identically.

## Safety plan examples

```text
Kettle + Repair:
  smoke/burning
  shock/sparks/wires
  water inside
  plug/cord damage

Kettle + Compare:
  smoke/burning
  shock/sparks/wires
  water inside

Kettle + Recycle:
  smoke/burning
  shock/sparks/wires

Shaver + Repair:
  smoke/burning
  shock/sparks/wires
  damaged/swollen battery
  water inside

Shaver + Recycle:
  smoke/burning
  damaged/swollen battery
```

These plans are a UX prototype. The final assessed scope must still be aligned with the BA acceptance criteria and approved safety sources.

## Deliberate boundaries

- The prototype does not diagnose faults.
- It does not tell the user an appliance is safe.
- It does not claim complete recall coverage.
- It does not invent provider contact details or opening hours.
- It does not invent repair/replacement prices.
- Exact location is optional and not persisted by FixForward.
- Automatic model-price resolution remains future work until governed data supports it.
