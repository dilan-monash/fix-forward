# FixForward v1.6 usability-lab — Proposed User Stories and Acceptance Criteria

These are **prototype candidate requirements** for usability testing. They must not silently replace the formally approved Iteration-1 source of truth. The team/BA/mentor should accept, modify or defer each scope change.

## US1 — Choose what I want to do

**As a household user with a faulty appliance, I want to start from my goal so I can get useful help without learning FixForward's internal process.**

Acceptance criteria:

1. Landing page shows Repair, Compare costs, Recycle and I'm not sure without scrolling on common desktop layouts.
2. Each option uses plain household language and a one-sentence explanation.
3. Choosing a direct goal does not later force a redundant “choose your action” step.
4. Every goal still passes through the required appliance/safety/recall gate.

## US2 — Identify my appliance without expert knowledge

**As a user, I want to select an appliance and optionally enter brand/model so FixForward can use the detail I know without blocking me when I do not know everything.**

Acceptance criteria:

1. Exactly the approved six appliance families are available.
2. Category stays locked until family is selected.
3. Categories are alphabetic within family.
4. Brand is optional; max 60 characters; if supplied it must contain a letter and use common brand punctuation.
5. Model is optional; max 50 characters; common model punctuation and numeric-only real identifiers remain possible.
6. Model help explains typical label locations and says not to open/remove screws.
7. Changing family/category invalidates downstream safety/result/cost state.
8. Invalid input receives a field-specific error and focus.

## US3 — Understand possible recalls

**As a user who may not know what a product recall is, I want a simple explanation and cautious result so I know when to check the official notice.**

Acceptance criteria:

1. Product recall is explained in plain language the first time it matters.
2. Category-only input does not produce “not recalled”.
3. Exact reviewed model can produce “Your model may be affected by a product recall”.
4. Brand mismatch does not hide an exact model match; difference is explained.
5. Near/one-character-different model is suggestion only.
6. No exact match explicitly says it does not prove no recall.
7. Recall API outage is shown as unavailable and safety remains usable.
8. Possible recall links to the official Product Safety notice/search and takes priority over normal pathways.

## US4 — Complete a short product-specific safety check

**As a user, I want only relevant, understandable safety questions so I can answer from what I already know without being told to test a potentially unsafe appliance.**

Acceptance criteria:

1. Questions depend on appliance and selected goal.
2. Repair has up to four questions; Compare up to three; Recycle up to two; guided route up to five in the prototype rule set.
3. Battery question does not appear for kettle; can appear for shaver.
4. Each question has What does this mean? help, pictogram, example and no-test warning.
5. Answers are Yes / No / Not sure.
6. Not sure does **not** end the questionnaire; remaining relevant questions remain answerable/required.
7. Separate I'm not able to check this safely action ends inspection and routes cautiously.
8. One critical Yes triggers serious/high outcome regardless of other answers.
9. Caution-only Yes produces a distinct attention-needed outcome.
10. Not sure without critical Yes produces uncertain outcome.
11. No-warning result is never labelled “safe”.

## US5 — Act after a serious warning

**As a user who reports a serious warning, I want a clear safe next step and disposal information if needed without being sent to an unsuitable community repair event.**

Acceptance criteria:

1. Serious result starts with Stop using this appliance for now.
2. User is not told to keep testing it.
3. Community Repair Café and normal cost comparison are not offered.
4. Qualified appliance repairer/electrician and official safety guidance are primary actions.
5. Controlled recycling/disposal planning is available.
6. Disposal screen says not to transport hot, smoking, leaking or actively damaged appliance.
7. Facility acceptance is not claimed without evidence.
8. Possible recall remains priority when present.

## US6 — Choose repair location or cost after a clear Repair check

**As a user who chose Repair, I want to decide whether to find somewhere to repair it or understand the money side.**

Acceptance criteria:

1. Clear Repair result opens a Repair hub.
2. Repair hub has Find repair options and Estimate & compare costs.
3. Repair evidence visual appears below those practical choices.
4. Browser Back returns to the expected prior step.

## US7 — Find an area quickly

**As a Melbourne user, I want suburb/postcode suggestions as I type so I do not need to know the exact formatting.**

Acceptance criteria:

1. Manual search accepts suburb or 4-digit postcode.
2. Partial postcode is allowed for suggestions but not final search.
3. Typing `312` shows matching 312x postcode/suburb pairs when present.
4. Typing a suburb prefix returns matching suburbs case-insensitively.
5. Suggestion selection works by mouse/touch.
6. Arrow Up/Down, Enter and Escape work by keyboard.
7. Active option uses appropriate combobox/listbox ARIA state.
8. Input max 50 characters; malformed input is rejected before search.

## US8 — Find nearby services

**As a user, I want nearby repair/recycling results inside FixForward so I can see practical contact and direction information without first understanding the data source.**

Acceptance criteria:

1. User can choose Use my current location or manual area search.
2. Geolocation is requested only after explicit action.
3. Exact coordinates remain in browser memory and are not written to Neon.
4. Results can filter by radius/provider type where relevant.
5. Result cards show name/address and available phone/hours/actions before provenance.
6. Call, Directions and Website appear only when supported.
7. Missing fields are not invented.
8. In-app map appears when coordinates/results support it.
9. Map failure/hang does not remove the service list; bounded fallback occurs.
10. Community Repair Café is excluded from caution/high-risk professional contexts.

## US9 — See repair history without mistaking it for a prediction

**As a user, I want a simple visual showing how similar appliance types have gone at repair events.**

Acceptance criteria:

1. Stacked visual shows Fixed / Repairable with more work / Other outcomes.
2. Actual counts and percentages are visible.
3. Chart occurs after the practical Repair choices/results.
4. Evidence source/sample/geography/mapping is expandable.
5. UI does not claim model-specific repair probability.

## US10 — Get smart cost context without fake precision

**As a user, I want FixForward to use the appliance/problem details I provide and show cost information it can actually support.**

Acceptance criteria:

1. Problem description requires 5–300 characters and meaningful words.
2. Problem grouping is explained as context, not diagnosis.
3. Entered brand+model is not called price-verified unless a governed product-price catalogue actually confirms it.
4. Unsupported/wrong model falls back to brand/category context instead of generating exact-model price.
5. Published repair-service fee examples show source links and retrieval context.
6. Different service models are not combined into one fake repair-cost range.
7. UI says the examples are not the user's exact quote and parts/additional work can change cost.
8. No replacement price is generated without approved evidence.
9. v1.6 sends no problem text to an external AI service.

## US11 — Compare real prices I have

**As a user who already has a repair quote and replacement price, I want a simple neutral comparison.**

Acceptance criteria:

1. Both values must be positive numbers.
2. Maximum two decimal places.
3. Amounts above AUD 100,000 are rejected by prototype sanity rule.
4. Text, blank, negative and zero invalid states receive specific messages.
5. Difference arithmetic is correct for repair lower, replacement lower and equal values.
6. Result says only which entered upfront amount is lower/equal.
7. Result states lower upfront price does not automatically mean better.
8. Cost values remain browser-memory only in current design.

## US12 — Preserve privacy and integrity

**As a user, I want the tool to minimise personal-data handling and fail cautiously.**

Acceptance criteria:

1. No account/password/payment/upload/history feature.
2. No journey-answer POST endpoint.
3. No journey answers in localStorage/sessionStorage/cookies.
4. Exact device coordinates not persisted or sent to Neon.
5. Technical failures are never described as safety/recall clearance.
6. Application DB access is read-only/SELECT-only by design.
7. Dynamic text is escaped.
8. Official recall URLs are restricted appropriately by backend.
9. Unexpected API error response is generic and does not expose sensitive internals.

## Approval note

US1, parts of US4–US10 and geolocation/autocomplete/cost-source behavior are prototype scope changes. Add an explicit BA/mentor **Accepted / Modified / Deferred** field before these become final Iteration-1 stories.
